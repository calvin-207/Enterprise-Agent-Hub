# Enterprise-Agent-Hub 本地部署与功能验收指南（macOS）

> 文档版本：2026-11-19 · 适用：GitHub `main` 当前版本（P1-A～P2-B、系统配置 → AI 模型管理 / 同步模型）。目标：从零启动后台与前端，先完成无付费模型的 Mock Agent 闭环，再按需验证供应商模型同步。
>
> **本指南的部署命令已根据仓库的实际 `backend/config.py_template`、`frontend/vite.config.js`、`frontend/src/config/index.js` 与管理命令整理。** CI 通过不等于你的 Mac 已部署成功；最终请以本地验收结果为准。

## 0. 先确认本次验收范围

| 模块 | 期望结果 | 是否需要真实 API Key |
|---|---|---|
| 后台登录、菜单 | 使用自己设置的 SuperAdmin 密码登录；找到 Agent 管理、Agent 执行、Agent 会话，以及「系统配置 → AI 模型管理」 | 否 |
| Django / Redis / Celery / Outbox | 各进程正常工作，AgentRun 从 QUEUED 进入终态 | 否 |
| Mock Agent | 模拟销售数据分析、RunStep/RunEvent、历史会话连续追问 | 否 |
| 同步 Mock 模型 | 同步完成，重复同步不重复创建，已有配置不被覆盖 | 否 |
| OpenAI / OpenAI 兼容模型同步 | 填写 Provider、Base URL、Key，点「同步模型」后导入本地模型列表 | 是 |
| 二次配置模型 | 同步的新模型默认关闭；已知模型自动填 USD 参考价，手动核对并设置启用和默认模型 | 同步完成后不需要 |
| 真实模型推理 | 给 Agent 发布真实模型版本，执行一次试验任务 | 是；需单独验证 SDK / Function Calling 兼容性 |

**重要限制：**“同步到模型列表”只证明供应商的模型目录接口可读，**不证明对应模型能完成聊天、工具调用或计费准确**。平台目前的业务工具主要是只读的 `mock_sales_summary`，不是 ERP 真数据。SSE 推送的是执行状态/事件，不是逐字 Token 流。

## 1. 准备本地环境

推荐 Mac（Apple Silicon / Intel 均可），终端使用 zsh。安装：

- Git
- Python **3.11**
- Node.js **20 LTS 或兼容版本**、npm
- Redis **7**（单机开发）
- 可选：PostgreSQL。**本指南首次跑通采用 SQLite**，无需先安装 MySQL/PostgreSQL。

先自检：

```bash
git --version
python3.11 --version
node -v
npm -v
```

任选其一启动 Redis。

**方式 A：Homebrew：**

```bash
brew install redis
brew services start redis
redis-cli ping
```

预期输出：

```text
PONG
```

**方式 B：Docker：**

```bash
docker run -d --name eah-redis -p 127.0.0.1:6379:6379 redis:7-alpine
docker exec eah-redis redis-cli ping
```

> 如果 Redis 容器已创建，改用 `docker start eah-redis`；如 6379 被占用，请先检查现有实例。**不要执行 `redis-cli FLUSHALL`**，避免删除本机其他项目数据。仓库目前没有根目录 `docker-compose.yml`，本指南采用本地多终端运行。

## 2. 拉取仓库并创建 Python 虚拟环境

```bash
git clone https://github.com/calvin-207/Enterprise-Agent-Hub.git
cd Enterprise-Agent-Hub
git switch main
git pull --ff-only

cd backend
python3.11 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

后续打开新的后端终端，都先执行：

```bash
cd /你的路径/Enterprise-Agent-Hub/backend
source .venv/bin/activate
```

> 请将示例 `/你的路径/` 替换成实际克隆目录。切勿将 `.venv`、`config.py`、明文 API Key 提交仓库。

## 3. 生成本地 config.py（必做）

仓库仅跟踪 `backend/config.py_template`，主 `settings.py` 使用 `from config import *`，**不会自动读取 `.env` 文件**。

```bash
cd backend
cp config.py_template config.py
```

打开 `backend/config.py`，本地首次验收把下列字段改为：

```python
DATABASE_TYPE = "SQLITE3"
REDIS_HOST = "127.0.0.1"
REDIS_PORT = "6379"
REDIS_PASSWORD = ""
REDIS_URL = f"redis://{REDIS_HOST}:{REDIS_PORT}"  # 本地 Redis 无密码时，避免留空密码前缀
DEBUG = True
ALLOWED_HOSTS = ["localhost", "127.0.0.1"]
DOMAIN_HOST = "http://127.0.0.1:9999"
```

`config.py_template` 里的默认 `DATABASE_TYPE` 为 `MYSQL`，若不改则会尝试连接 MySQL。其余字段（例如登录限制、接口权限配置）保留模板默认值即可。

先验证配置：

```bash
python manage.py check
```

**若此处提示 `No module named config`**，说明没有正确执行 `cp config.py_template config.py` 或工作目录不在 `backend`。

## 4. 数据库迁移与初始化

在 **backend 虚拟环境**中执行：

```bash
python manage.py migrate
python manage.py bootstrap_mock_catalog
```

首次设置唯一管理员密码（替换为**你自己的强密码**；示例占位不可照抄）：

```bash
export INITIAL_SUPERUSER_PASSWORD='换成你自己的随机强密码'
python manage.py init
unset INITIAL_SUPERUSER_PASSWORD
```

管理员账号名称：`SuperAdmin`。后续重复运行普通 `python manage.py init` 是为了更新菜单，不会主动重置密码。已有数据库升级时，**不要使用 `python manage.py init -y`**，该选项可能重建初始化数据。

如果已经初始化但没有配置管理员密码，可执行：

```bash
python manage.py changepassword SuperAdmin
```

## 5. 可选：配置服务端加密密钥（真实 Provider 的后台 Key 录入需要）

**只做 Mock 测试可以跳过本节。** 如果要在「AI 模型管理」页面输入 API Key 并加密保存，必须向 **Django API 进程和 Celery Worker 进程注入同一把 Fernet 密钥**。

在本地安全终端生成（仅输出到本机终端，勿贴到聊天/工单）：

```bash
cd backend
source .venv/bin/activate
python -c 'from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())'
```

将生成的值保存在本机密码管理器或 Secret Manager。启动 Django、Celery 前在各自终端设定：

```bash
export EAH_MODEL_ENCRYPTION_KEY='这里是你自己生成的密钥'
```

使用 OpenAI 兼容供应商时，Base URL 须为**公网可解析的 HTTPS 地址**，路径按供应商文档填写（内置模板：DeepSeek、智谱、Kimi、通义千问、Gemini、Claude 等，新增 Provider 时可直接选择自动填充）。MVP 已移除 `EAH_MODEL_ALLOWED_HOSTS` 域名白名单与 `/v1` 路径硬性要求（2026-11-19），无需配置环境变量或重启进程；当前逻辑仍拒绝非 HTTPS URL、带凭据/查询参数的 URL，以及解析到非公网地址的服务，本地 `http://localhost:xxxx/v1` 不能当作可同步的供应商。官方 OpenAI 不需要手动填写 Base URL，使用固定官方地址。

另一种方式是**不在后台填写 API Key**：在后端和 Worker 启动环境里设置 `EAH_MODEL_KEY_MAIN`，后台 Provider 填 `secret_ref=env:EAH_MODEL_KEY_MAIN`。**后台 Key 和环境变量引用应二选一。**

## 6. 启动进程（建议至少开 4 个终端）

> **环境匹配提示**：同一套部署的 Django / Worker / Beat 必须使用相同的 `HUB_ENV`
> （默认 `dev`）。默认队列 `hub-<HUB_ENV>`、消息环境头与版本戳都由它推导：
> 测试任务不会流进正式环境队列；拉取代码后请重启 Worker/Beat，否则旧进程会因
> 版本戳不一致拒绝执行新消息（自动化任务页会显示「Worker 拒绝执行」并可重试）。
> 多台机器共用同一个 Redis 时，给每台机器设置不同的 `HUB_ENV`（如 `dev-alice`）。

**终端 A：Django 后端（使用 9999 端口）**

```bash
cd /你的路径/Enterprise-Agent-Hub/backend
source .venv/bin/activate
# 如使用后台保存的真实 Provider Key，先 export EAH_MODEL_ENCRYPTION_KEY
daphne -b 127.0.0.1 -p 9999 main.asgi:application
```

也可临时使用 `python manage.py runserver 127.0.0.1:9999` 调试普通接口；建议使用 Daphne 验证 ASGI SSE。

**为什么是 9999？** 项目当前 `frontend/vite.config.js` 的 `/api` 代理目标与 `frontend/src/config/index.js` 的开发 API_HOST 都指向 `127.0.0.1:9999`。直接照旧 README 运行 `8000`，会导致前端 8081 页面加载正常、接口却无法连接。

**终端 B：Celery Worker**

```bash
cd /你的路径/Enterprise-Agent-Hub/backend
source .venv/bin/activate
export HUB_ENV=dev   # 与终端 A 相同；不加 -Q，自动只消费 hub-dev 队列
# 真实模型：此终端必须配置与 Django 相同的加密密钥/允许的域名
celery -A main worker --loglevel=info --concurrency=2
```

**终端 C：Agent Outbox Dispatcher（必须）**

```bash
cd /你的路径/Enterprise-Agent-Hub/backend
source .venv/bin/activate
python manage.py dispatch_agent_outbox --interval 2
```

若不启动 Dispatcher，AgentRun 可能一直是 `QUEUED`；若不启动 Worker，Outbox 已派发但任务不会被处理。

**终端 D：Vue 前端**

```bash
cd /你的路径/Enterprise-Agent-Hub/frontend
npm install
npm run dev
```

浏览器打开：

**http://127.0.0.1:8081**

Vite 当前配置的开发端口为 `8081`，且 `strictPort: true`，若被占用将直接报错。

**前端入口结构（SEO 落地页 + 控制台）：**

| 路径 | 内容 | 说明 |
|---|---|---|
| `/` | 官网 SEO 落地页 | 静态可抓取内容（`frontend/index.html`）；「立即登录」直接弹出登录框，调 `/api/token/` 成功后携带 token 进入 `/app/#/home`（无 JS 时兜底跳转原登录页） |
| `/app/`（或 `/app`） | 管理控制台 SPA 入口 | 即原登录页所在应用，hash 路由如 `/app/#/login`、`/#/register` |

- 旧书签 `/#/login` 会由落地页内的一段兼容脚本自动跳转到 `/app/#/login`，原登录页功能不变。
- 集成部署（Django 直出）时由 `backend/main/urls.py` 渲染：`/` → `leeadmin/index.html`（落地页），`/app/` → `leeadmin/app.html`（SPA）；构建命令为 `npm run build:backend`。
- 上线绑定正式域名后：替换 `frontend/public/sitemap.xml` 与 `robots.txt` 中的占位域名，并取消 `frontend/index.html` 头部 canonical / og:url 注释。

**官网落地页文案后台配置（系统配置 → 官网 SEO）：**

落地页的 SEO 标题、摘要、关键词、版权信息、ICP 备案号由后台配置驱动（服务端渲染，修改后刷新即生效，无需重新构建前端）：

| 配置项 | 变量名 | 说明 |
|---|---|---|
| SEO 标题 | `seo.title` | 浏览器标签与搜索结果标题（同时写入 og:title / twitter:title） |
| SEO 摘要 | `seo.description` | meta description 与结构化数据描述 |
| SEO 关键词 | `seo.keywords` | meta keywords |
| 版权信息 | `seo.copyright` | 落地页页脚版权文案 |
| ICP 备案号 | `seo.icp` | 页脚备案号，**留空则不渲染备案区块** |

- 顶部品牌名与登录弹窗标题使用「基础配置 → 系统标题」（`base.systitle`）。
- 配置分组由 `python manage.py init` 幂等种入（重复执行不会覆盖已修改的值）；未初始化时落地页使用 `backend/system/seo_defaults.py` 的兜底文案。
- 开发环境 `npm run dev` 时，`/` 会代理到后端 9999 由 Django 渲染（保证与线上一致），因此本地改 `frontend/index.html` 源码后需重新 `npm run build:backend` 才能在 `/` 预览；改后台配置则即时生效。
- 修改后端代码（含本功能的视图/序列化器）后，**Daphne 不会自动重载**，需重启后端进程。

**可选终端 E：Celery Beat，仅当测试 Cron 定时计划时启动**

```bash
cd /你的路径/Enterprise-Agent-Hub/backend
source .venv/bin/activate
celery -A main beat --scheduler django_celery_beat.schedulers:DatabaseScheduler --loglevel=info
```

同一环境 Beat **只能运行一个实例**。仅测试 Agent 会话、手动运行和模型同步时，不必启动 Beat。

启动 Beat 后，内置的 `system.ops_heartbeat` 调度会每分钟向 Redis 上报一次心跳，「运维管理」看板的 Beat / Worker 心跳状态即来源于此；未启动 Beat 时该看板会提示心跳未上报（预期行为，正好用于判断 Beat 是否存活）。

## 7. 验收 1：后台登录与菜单

1. 打开 `http://127.0.0.1:8081`，应显示官网 SEO 落地页；点击「立即登录」直接弹出登录框（含验证码），使用 `SuperAdmin` 和你初始化时的密码登录，成功后自动进入控制台 `/app/#/home`。
2. 确认菜单至少包括 **Agent 管理、Agent 执行、Agent 会话、自动化任务、定时任务计划**。
3. 打开 **系统配置 → 运维管理**，确认看板展示 7 张状态卡片：CPU、内存、磁盘、数据库、Redis 缓存、Celery Worker（数量、并发、最近心跳）、Celery Beat（调度心跳）。本地开发常见的预期提示：单并发 Worker（`--pool=solo` 或 `--concurrency=1`）会标注"任务执行期间会阻塞后续任务"；未启动 Beat 时 Beat 卡片显示"心跳未上报"。看板支持手动刷新与 10/30/60 秒自动刷新；主机资源数据依赖 `psutil`（已收录在 `backend/requirements.txt`）。
4. 切换到 **系统日志** Tab：下拉选择 `backend/logs/` 下的日志文件（server.log、error.log 及各进程日志），可按 100/200/500 行读取尾部日志并按关键字过滤。点击概览中 Worker 卡片里的节点行，可下钻查看该节点的并发、进程 PID、运行时长、累计执行任务数、高频任务 Top 与正在执行的任务。
5. 展开 **系统配置 → AI 模型管理**，应进入 `/modelManage`。
6. 在模型管理看到两个页签：**模型提供商**、**模型列表与价格**。
7. 如果升级已有数据库后看不到新菜单，先重新运行 `python manage.py init`，刷新登录状态，并核对该菜单对当前管理员角色是否可见。
8. （已执行 4.1 种子时）分别用 `test_admin`、`test_dept_mgr`、`test_user` 登录，核对各自可见菜单与上表一致；`test_user` 不应看到「组织与权限」与「系统配置」目录；`test_frontend`（前端用户）不出现在「用户管理」列表（该列表仅显示后台账号 identity=1）。

验收记录：页面是否显示、后端接口是否返回成功、浏览器控制台有无 401/403/404/500。

## 8. 验收 2：完全离线的 Mock Agent（强烈建议先测）

### 8.1 准备演示模型和工具

之前执行的：

```bash
python manage.py bootstrap_mock_catalog
```

会创建 `mock` Provider、`mock-small` 模型、只读 `mock_sales_summary` 工具，重复执行不会重复创建。

打开「系统配置 → AI 模型管理」，确认 Mock Provider 和模型存在且已启用。如你曾手动停用，应在页面重新启用。Mock 不需要 API Key。

### 8.2 创建并发布 Agent

在 **Agent 管理**：

1. 点击“创建 Agent”，例如：唯一标识 `demo-sales-agent`，名称 `演示销售分析 Agent`。
2. 进入“版本 → 新建版本”。
3. 系统提示词可填：`仅根据已授权的 mock_sales_summary 虚构数据回答，不得声称它是真实业务数据。`
4. 模型选择 `mock / mock-small`。
5. 工具选择 `mock_sales_summary`。
6. 保存草稿，点击“发布”。
7. 若使用单独业务用户登录，需要在“用户授权”中明确授予该用户 `run` 权限；超级管理员拥有平台管理员运行权限。

发布后版本不可直接编辑；如需更改，请新建版本。

### 8.3 执行与检查

进入 **Agent 执行**（`/agentRuns`），选择刚发布的 Agent，输入：

```text
分析本月销售情况
```

点击“提交执行”，观察：

```text
QUEUED → RUNNING → SUCCEEDED
```

详情里应该看到：

- Agent 分析结果，明确注明虚构数据；
- `RunStep` 至少有 `DISPATCH / TOOL_READ / MODEL_CALL`；
- `RunEvent` 包含 `run.queued / run.started / run.step_completed / run.completed`；
- 模拟数据：**2026-09 = 125000 元，2026-10 = 115000 元，10 月环比 -8%**；
- `ModelUsage` 中 Mock 的 Token 值为 0（不代表真实模型费用）。

如果卡在 QUEUED，重点检查终端 C 的 Dispatcher；若没有执行步骤，重点检查 Celery Worker 的日志。

### 8.4 连续会话与追问

进入 **Agent 会话**（`/agentChat`）：

1. 选择演示 Agent，新建会话。
2. 第一轮输入：`分析9月销售额`，确认成功。
3. 第二轮输入：`继续分析刚才那个月`，确认结果仍能引用 **2026-09**。
4. 刷新浏览器，重新打开同一会话，确认历史消息仍在。
5. 执行过程应可看到状态事件；断网恢复后通过游标重新补查。注意 SSE 是运行事件，不是逐字 Token。

## 9. 验收 3：系统设置 → AI 模型管理 → 同步模型

### 9.1 先测 Mock 同步（无需外网）

1. 进入 **系统配置 → AI 模型管理 → 模型提供商**。
2. 找到 `mock` Provider；确认是“启用”状态。
3. 点击 **同步模型**。
4. 应显示模型总数、已存在/新增数；列表中能找到 `mock-small`。
5. 再点击一次同步：不应新增相同 `provider + model_code` 的重复模型。
6. 如果已修改 Mock 模型名称、Token 单价或启停状态，重复同步**不应覆盖你手工的选择**。

### 9.2 真实 OpenAI 模型同步

准备好自己有权限使用的供应商账号、合法 API Key，且本机可以访问相关服务。

1. **模型提供商 → 新增 Provider**，类型选择 **OpenAI 官方**。
2. 供应商标识填写例如 `openai-main`、名称自定义。
3. 以下两种方式**选一种**：
   - 在后台 API Key 输入框填入 Key（前提是已为 Django 进程和 Worker 配置 `EAH_MODEL_ENCRYPTION_KEY`）；
   - 后台只填 `env:EAH_MODEL_KEY_MAIN`，并在 Django 与 Worker 终端安全注入 `EAH_MODEL_KEY_MAIN`。
4. 勾选启用，点击保存。API 查询应**只回显“已存储密钥”状态**，不能返回明文 Key。
5. 在 Provider 列表点击 **同步模型**。
6. 成功后进入“模型列表与价格”，按当前供应商筛选，确认有模型 ID 导入本地。
7. 选择一个供应商实际允许你使用的聊天/工具模型：内置价目表覆盖的模型（DeepSeek、OpenAI、Claude、Gemini、Kimi、GLM、Qwen 主流型号）在同步时已自动填入名称、参考单价与输出上限，核对/修正后开启并可设为默认；未覆盖的模型仍需手动填写。
8. 返回 Agent 管理 → 新建 Agent 版本，确认模型可以在列表中被选择。

**注意：**模型目录 API 返回的模型列表可能包含你不能实际调用的模型、非聊天模型、工具调用不兼容的模型。价格来自**内置参考价目表**（`model_gateway/pricing_reference.py`，2026-11 快照，USD/百万 Token，国内供应商为官网人民币价近似换算）——**仅供费用估算，不是官方实时价格，请以供应商官网为准**；**0 价格仍是“尚未配置”，不意味着免费**。参考价只在同步创建新记录时填充，绝不覆盖管理员已设置的值。

### 9.3 OpenAI 兼容供应商的同步

1. 在「新增 Provider」对话框顶部选择**快速模板**（如 DeepSeek / 智谱 GLM / Kimi / 通义千问 / Gemini / Claude），标识、名称、适配类型和 Base URL 会自动填充；也可 Provider 类型选 **OpenAI 兼容接口** 手动输入完整 HTTPS 地址，例如 `https://api.your-provider.example/v1`。MVP 已移除域名白名单，无需运维预先放行。
2. 填写安全保存的 Key 或环境变量引用，保存并启用。
3. 点击 **同步模型**，观察接口是否成功返回列表。
4. 如成功，仅表示该供应商提供兼容 `/models` 列表；真正执行 Agent 需进一步验证 OpenAI SDK 的聊天和 Tool Calling 能力。

**不可用场景：**私有 IP、localhost、HTTP、非 `/v1` 路径、原生非 OpenAI 兼容的模型列表接口，当前都会被拒绝或无法正常同步。

### 9.4 二次同步验证

手动调整某个同步模型的：

- 模型名称；
- 启用/关闭状态；
- 输入/输出 Token 单价；
- 默认标记。

然后再次点击“同步模型”。**这四类本地配置应保持不变**，已有模型只刷新 `last_seen_at`。已绑定到 AgentVersion 的模型引用不会被重建。

## 10. 验收 4：真实模型最小推理（可选，可能产生费用）

当模型已经同步、**确认模型支持当前 SDK 的 Agent 和 Function Calling**、已手工设置价格、并完成 Agent 新版本发布后：

1. 确认 Django 进程和 Worker 进程都能解密或读取该 Provider 的 API Key。
2. 使用仍为只读的 `mock_sales_summary` 工具发布新的 AgentVersion。
3. 在 Agent 执行中心提交一条简短、无敏感数据的问题，检查 Run 状态、失败码和 Worker 日志。
4. 若成功，查看模型的 Token 用量和估算成本；若 Token 为未知，不要当作零用量。
5. 将估算费用与真实供应商账单对照，记录模型名称、模型 ID、HTTP 结果和偏差。

请先设置足够低的供应商消费限额、避免输入客户真实数据。**真实付费模型调用和第三方兼容性未由本指南预先保证成功**，遇到失败优先记录错误码及经过脱敏的日志。

## 12. 常见问题排查

| 现象 | 最先检查 | 处理方向 |
|---|---|---|
| `ModuleNotFoundError: config` | `backend/config.py` 是否存在 | `cp config.py_template config.py` |
| Django 启动连接 MySQL 失败 | `DATABASE_TYPE` 是否仍为 `MYSQL` | 本地先改为 `SQLITE3`；再执行 `migrate` |
| 前端能打开，登录接口失败 | Django 是否运行在 9999 | 检查 `vite.config.js` 代理、`src/config/index.js` 的 API_HOST |
| Redis 连接失败 | `redis-cli ping`、`REDIS_URL` | 确保本机 Redis 已启动、密码与端口对应 |
| AgentRun 长时间 `QUEUED` | Dispatcher 和 Worker | 启动 `dispatch_agent_outbox`、查看 Celery 日志和 Redis DB3 |
| 看到 `FAILED` | Run 详情 `error_code` | 检查模型启用、工具权限、密钥、预算与 Worker 错误码 |
| Agent 模型列表为空 | ModelProfile / Provider 的启用状态 | 同步模型后手动启用；Mock 可用 bootstrap 命令 |
| 模型同步报 403 | 当前用户是否为超级管理员 | 切换 SuperAdmin；不能仅凭菜单授权越权使用 API |
| 模型同步报 502 | 供应商 Key、网络、模型列表协议 | 检查官方或兼容 `GET /v1/models`；不显示原始上游敏感错误 |
| API Key 无法保存（503） | `EAH_MODEL_ENCRYPTION_KEY` | Django 进程配置有效 Fernet 密钥并重启 |
| 自定义 Base URL 不合法 | 是否 HTTPS 公网地址 | 使用供应商文档给出的 HTTPS 地址（可先选模板）；不要使用私网地址 |
| SSE 无法实时显示 | Daphne / 代理 / 浏览器开发者工具 | 检查 `/stream/` 返回类型及 Authorization；状态最终以 Run 查询为准 |
| `npm run dev` 端口被占用 | 8081 是否已有服务 | 停止冲突进程；或同步修改前端设置 |
| 新菜单没有显示 | 是否运行 `init`、当前用户菜单权限 | 执行非破坏性 `python manage.py init`，重新登录 |
| 运维管理页 Worker/Beat 显示"心跳未上报" | Beat 与 Worker 是否已启动 | 启动后等待 1 个调度周期（60 秒）再刷新；CPU/内存/磁盘无数据则安装 `psutil` |
| 运维管理页数据库/Redis 卡片异常 | 对应服务连通性 | 按 `redis-cli ping`、数据库配置逐项排查，卡片消息会给出具体原因 |

**安全提醒：**请不要将 `config.py`、真实 Key、Fernet 密钥、`db.sqlite3`、带个人信息的日志推送 GitHub。寻求排错帮助时只分享错误码和脱敏日志。
